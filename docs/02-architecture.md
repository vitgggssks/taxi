# Архітектура

## 1. Принципи

1. **Модульний моноліт** з жорсткими межами модулів — кожен модуль можна винести в окремий сервіс
   без переписування бізнес-логіки (усі залежності — через `lib/*`).
2. **Домен понад UI.** Ціна, диспетчеризація, гроші, статуси живуть на сервері; клієнти лише
   відображають і надсилають команди. Жодних «демо-даних» у клієнтах.
3. **Усе налаштовується даними**, не кодом: тарифи, класи, опції, геозони, промокоди, параметри
   диспетчеризації, політика плюс/мінус, кешбек.
4. **Ідемпотентність і конкурентність** — властивість схеми БД, а не «обережність» у коді.
5. **Чесність меж**: якщо частина функціоналу не реалізована — це видно в документації.

## 3. Стейт-машина замовлення

```
searching ─► offered ─► assigned ─► driver_arriving ─► waiting ─► in_progress ─► completed
    │           │            │              │              │            │
    │           │            └──────────────┴──────────────┴────────────┴─► canceled
    │           └─► searching (таймер/відмова)      no_drivers ◄─► searching
    └─► no_drivers
```

`lib/order-service.ts` містить таблицю дозволених переходів; будь-яка спроба нелегального переходу
→ `409 conflict`. Адмін/диспетчер можуть форсувати скасування (`reason: 'force'`) — це логується.

## 4. Диспетчеризація (алгоритм)

1. Замовлення створюється зі статусом `searching`; виклик `tryDispatch()`.
2. Вибір кандидатів: `driver_profiles.status='verified' AND work_status='online'`, є активне авто
   потрібного класу, не має активної поїздки, відстань ≤ `search_radius_km × (1 + 0.7·(round−1))`,
   також ≤ власного `accept_radius_km`. Сортування за відстанню.
3. Якщо серед кандидатів є водій з `auto_accept=1` і ціна ≥ його `min_price_cents` — пропозиція
   створюється і приймається автоматично (в тій самій транзакції).
4. Інакше — до `parallel_offers` (типово 3) пропозицій одночасно, таймер `offer_timeout_s` (типово 20).
5. Перший прийнятий → решта `superseded`; замовлення `assigned`, водій `busy`.
6. Савеєр (2 с) протерміновує пропозиції, повертає водіїв у `online`, запускає наступний раунд.
   Після `offer_rounds` раундів → `no_drivers` (замовлення не втрачається: диспетчер може призначити
   вручну, а планувальник продовжує пробувати при зміні ситуації).
7. Планові замовлення «прокидаються» за 10 хв до `scheduled_at`.

Гарантія «одне замовлення — один водій»: частковий унікальний індекс
`uniq_order_accepted ON order_offers(order_id) WHERE status='accepted'` + перевірка
`orders.driver_id IS NULL` всередині транзакції.

## 5. Realtime

WebSocket `/ws?token=…`. Канали: `user:<id>`, `role:<role>`, `order:<id>`.
Сервер публікує: `order.updated`, `order.assigned`, `offer.new`, `offer.expired`, `driver.location`,
`notification`, `wallet.updated`. Клієнт підписується на `order:<id>` лише після перевірки прав.
Клієнти мають перепідключення з backoff і **resync через REST** (`GET /api/orders/:id`) — це і є
робота «при тимчасовій втраті інтернету».

## 6. Гроші

- Усі суми — цілі числа в копійках (`*_cents`), ніяких float.
- Ledger: `wallet_transactions` (акаунти `main` / `bonus`), кожен запис має `idempotency_key UNIQUE`.
- Модель готівки: пасажир платить водієві → з балансу водія списується комісія.
- Модель картки/гаманця: платформа збирає → водієві нараховується `нетто` (сума − комісія).
- Корпоратив: рахунок на період (`corporate_invoices`) + місячний ліміт співробітника + кредитний ліміт.
- Кешбек нараховується на бонусний рахунок у момент розрахунку замовлення.

## 7. Цільовий стек і шлях міграції

| Зараз (ця ітерація) | Цільовий прод | Що змінюється |
|---|---|---|
| Fastify + TS (модулі) | NestJS (модулі 1:1, DI поверх тих самих сервісів) | обгортки контролерів |
| SQLite (`better-sqlite3`) | PostgreSQL 16 + PostGIS | `lib/db.ts` + `lib/geo.ts` (ST_DWithin/ST_Contains), схема з `docs/03-data-model.sql` |
| У памʼяті (hub) | Redis pub/sub для WS-шарів | `lib/realtime.ts` |
| Савеєр у процесі | BullMQ/Redis + RabbitMQ для подій | `startWorkers()` |
| SVG-мапа | Google Maps Platform (тайли, геокодинг, route matrix) | `web/app/map.js`, `lib/geo.ts` |
| Симулятор еквайрингу | LiqPay/Fondy/Stripe | `captureWithGateway()` |
| OTP у відповіді API | SMS-провайдер (TurboSMS/Twilio) | `modules/auth.ts` (одна функція) |
| Web-клієнти | Flutter 3 (iOS/Android) поверх того ж API | клієнтський шар |

Схема БД уже написана в портативному підмножині SQL; PostGIS-версія лежить у `docs/03-data-model.sql`.

## 8. Масштабування

- Міста/регіони/країни — рядки в довідниках; тарифи й параметри диспетчеризації — на місто.
- Нові класи/послуги — дані, не код (`POST /api/admin/classes` клонує тарифи по всіх містах).
- Мультивалютність: `currency` у місті/тарифі/замовленні.
- Багатомовність: `users.locale`, рядки UI зібрані в клієнтах (i18n-шар — roadmap).
- Гарячі шляхи (пошук водія, ціна) не залежать від кількості міст; геопошук індексується
  (`GIST` на `geography` у PostGIS, `idx_orders_status`, `idx_offers_driver`).

## 9. Тестування

`npm test` — 37 інтеграційних тестів на реальному HTTP+БД (`app.inject`, in-memory SQLite):
авторизація/OTP, ціноутворення (мін. тариф, опції, зупинки, ліміт плюс/мінус), диспетчеризація
(прийняття, гонка двох водіїв, таймаут і повторна пропозиція, авто-прийняття, no_drivers, ручне
призначення), ліміт 5 активних замовлень, промокоди, зміна маршруту, повний цикл поїздки з
розрахунком, скасування з компенсацією, ідемпотентність платежу, доставка з кодами, реєстрація й
верифікація водія, адмін-агрегати/аудит/CSV, корпоративні ліміти, підтримка.
